CLI local · Jira + GitHub + GitLab

Sua avaliação semestral merece dados, não achismo.

dev-metrics roda na sua máquina e gera um relatório das suas entregas no Jira e da sua atividade de código no GitHub e GitLab, num intervalo de datas. Você usa os seus próprios tokens — nada sai do seu computador.

3 fontes de dados· 100% local· MIT license 
$ npx @feliperold/dev-metrics --from 2026-01-01 --to 2026-06-30

Sem instalação prévia. O relatório sai em ./reports, em Markdown e Excel.

Antes de rodar

3 ideias erradas sobre essa avaliação.

Seis meses é tempo demais pra depender da memória. Entre entregar feature, revisar PR e apagar incêndio, é fácil esquecer metade do que você fez. O relatório busca os dados direto nas fontes — pela data de resolução de cada issue e de cada PR/MR — não pela sua lembrança.

"10 PRs mergeados" não diz se foram 10 ajustes pequenos ou 2 PRs enormes contados junto com retrabalho. Por isso o relatório sempre devolve o número com contexto: issues por tipo, story points com média e mediana, tamanho mediano de PR em linhas e arquivos alterados. Métrica isolada é fácil de interpretar mal.

Não precisa. Cada pessoa roda a CLI pra si mesma, com os próprios tokens, e só consulta dados aos quais já tem acesso. Nenhum dado passa por um servidor central — o relatório é gerado e fica na sua máquina, em reports/, fora do controle de versão.

Do token ao relatório

Três passos, sem planilha manual.

01

Configure os tokens

Um .env com as credenciais do Jira, GitHub e/ou GitLab. O Jira é obrigatório; pelo menos uma das outras duas também.

02

Rode o comando

dev-metrics --from <data> --to <data>. As duas datas são inclusivas, e cada evento é contado pela data em UTC.

03

Leia o relatório

Markdown com os números em contexto e um .xlsx com uma aba por fonte, pronto pra levar pra reunião de avaliação.

O que entra no relatório

Métricas cobertas.

Cada fonte tem a própria seção, calculada só com os dados dela. Se uma fonte falhar, a seção dela fica marcada como incompleta — o resto do relatório continua.

Jira

Entregas por tipo

Issues concluídas no período, agrupadas por tipo, mais média e mediana de story points — "no data" quando ninguém tem estimativa.

GitHub / GitLab

PRs e MRs

Abertos, mergeados e fechados sem merge no período — cada plataforma com a própria contagem, sem misturar os números.

Tamanho

Mediana de linhas e arquivos

Só nos PRs/MRs mergeados no período. Mediana, não média — um PR gigante não distorce o resultado.

Velocidade

Cycle time

Horas entre a abertura e o merge de cada PR/MR, em média e mediana. É o tempo de código, não o tempo de status do Jira.

Commits

Commits no período

Só os do próprio usuário autenticado, com data dentro do intervalo escolhido.

Confiabilidade

Falha parcial, nunca silenciosa

Se uma fonte falhar, o relatório sai com a seção marcada como incompleta e o motivo — a CLI também sai com código de erro diferente de zero.

Segurança

Eu rodo localmente. É daí que vêm seus dados.

Tokens só por variável de ambiente. Nunca aparecem no relatório, nos logs ou em mensagens de erro.

Cabeçalho, nunca URL. Os tokens vão em Authorization ou PRIVATE-TOKEN — nunca na query string.

reports/ fora do git. O relatório contém dados de avaliação de uma pessoa, então nunca entra no controle de versão.

Identidade pelo próprio token. A CLI descobre quem é você via /myself, /user — não cruza identidades entre sistemas.

JIRA_BASE_URL=https://sua-empresa.atlassian.net
JIRA_EMAIL=voce@empresa.com
JIRA_API_TOKEN=••••••••••••
GITHUB_TOKEN=••••••••••••
GITLAB_TOKEN=••••••••••••
# fica em .env, já ignorado pelo .gitignore

Instalação

O próximo passo é rodar na sua própria máquina.

Node 24 ou superior. Sem conta, sem cadastro — só os tokens das plataformas que você já usa.

$ npm install -g @feliperold/dev-metrics
$ dev-metrics --from 2026-01-01 --to 2026-06-30
