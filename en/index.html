Your performance review deserves data, not guesswork.

Before you run it

3 wrong ideas about this review.

Six months is too long to rely on memory. Between shipping features, reviewing PRs, and firefighting, it's easy to forget half of what you did. The report pulls data straight from the source — by each issue's resolution date and each PR/MR's merge date — not from your recollection.

"10 PRs merged" doesn't say whether that was 10 small tweaks or 2 huge PRs counted alongside rework. That's why the report always returns the number with context: issues by type, story points with average and median, median PR size in lines and changed files. An isolated metric is easy to misread.

You don't. Each person runs the CLI for themselves, with their own tokens, and only looks at data they already have access to. No data passes through a central server — the report is generated and stays on your machine, in reports/, outside version control.

From token to report

Three steps, no manual spreadsheet.

01

Set up the tokens

A .env with your Jira, GitHub and/or GitLab credentials. Jira is required; at least one of the other two is too.

02

Run the command

dev-metrics --from <date> --to <date>. Both dates are inclusive, and each event is counted by its UTC date.

03

Read the report

Markdown with the numbers in context, plus an .xlsx with one tab per source, ready to bring to your review meeting.

What goes into the report

Metrics covered.

Each source has its own section, calculated only from its own data. If a source fails, its section is flagged as incomplete — the rest of the report still goes through.

Jira

Deliveries by type

Issues completed in the period, grouped by type, plus average and median story points — "no data" when nobody has an estimate.

GitHub / GitLab

PRs and MRs

Opened, merged, and closed without merge in the period — each platform with its own count, never mixed together.

Size

Median lines and files

Only for PRs/MRs merged in the period. Median, not average — one giant PR won't skew the result.

Speed

Cycle time

Hours between opening and merging each PR/MR, in average and median. It's code time, not Jira status time.

Commits

Commits in the period

Only the authenticated user's own commits, dated within the chosen range.

Reliability

Partial failure, never silent

If a source fails, the report still ships with that section flagged as incomplete and why — the CLI also exits with a non-zero error code.

Example output

The report, in Markdown.

Security

I run locally. That's where your data comes from.

Tokens only via environment variables. They never show up in the report, the logs, or error messages.

Header, never URL. Tokens travel in Authorization or PRIVATE-TOKEN — never in the query string.

reports/ stays out of git. The report contains one person's review data, so it never goes into version control.

Identity from the token itself. The CLI figures out who you are via /myself, /user — it never cross-references identities across systems.

JIRA_BASE_URL=https://your-company.atlassian.net
JIRA_EMAIL=you@company.com
JIRA_API_TOKEN=••••••••••••
GITHUB_TOKEN=••••••••••••
GITLAB_TOKEN=••••••••••••
# lives in .env, already ignored by .gitignore

Install

The next step is running it on your own machine.

Node 24 or higher. No account, no signup — just the tokens for the platforms you already use.

$ npm install -g @feliperold/dev-metrics
$ dev-metrics --from 2026-01-01 --to 2026-06-30
